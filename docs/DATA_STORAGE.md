# Локальная база и перенос

## Короткая инструкция: где взять файл базы

В Next рабочая база не лежит в файле рядом с HTML: это IndexedDB профиля
Chrome/Edge на текущем компьютере. Чтобы перенести её, откройте «База,
справочники и экспорт» → «Выгрузить архив Next». Браузер сохранит
`mac-analyzer-next-ГГГГ-ММ-ДД.madb.json` в свою папку загрузок (или покажет
выбранный браузером путь сохранения). Переместите архив в папку резервных копий,
на USB-диск или в защищённое хранилище. На целевом компьютере откройте Next,
выберите «Загрузить архив» и укажите сохранённый `.madb.json`. Импорт добавляет
данные и не удаляет записи, уже находящиеся в целевой базе. При использовании
блока «Папка данных» portable-архив в выбранной папке называется
`mac-analyzer-data.madb`.

При импорте `mac_analyzer_settings.json` поддерживаемые настройки переносятся
локально. Если JSON ссылается на отдельный `ip_address_mapping_file`, приложение
покажет действие повторного выбора: укажите этот CSV/XLSX через штатный импорт
IP→адрес и подтвердите колонки. Абсолютный путь не читается и не сохраняется.
Флаг `auto_detect_address_by_ip` переносится как переключатель подтверждённого
исторического обогащения по IP коммутатора. Next использует минимум два успешных
Final, три устройства, 90% согласия и показывает уверенность и доказательства;
legacy-автоматическое создание правил из одного результата не запускается.

Для переноса истории из старой PyQt-версии сначала закройте её. В типовой
Windows-Portable поставке проверьте каталог `data/legacy/` рядом с приложением:
там могут находиться `mac_history.db`, `vendor_model_history.db` и
`mac_analyzer_stats.db`. Если задана переменная `MAC_ANALYZER_DATA_DIR`, ищите
их в `<значение переменной>/legacy/`.

При самостоятельном запуске PyQt-скрипта каталога `data/legacy` может не быть:
классы `MACHistoryDatabase` и `VendorModelHistory` открывают по умолчанию
`mac_history.db` и `vendor_model_history.db` относительно рабочей папки процесса.
Если файлов нет в `data/legacy`, проверьте папку, указанную в поле «Рабочая
папка / Start in» ярлыка старой программы, или найдите там файлы с этими именами.
`mac_analyzer_stats.db`, если он есть, содержит отдельные статистические данные.

Для MAC Analyzer Pro Web основная SQLite-база называется
`mac_analyzer_web.db`. По умолчанию она находится в исходной папке Web-проекта:
`data/databases/mac_analyzer_web.db`. Если Web-приложение запущено с
`MAC_ANALYZER_DATA_DIR`, база лежит в
`<значение переменной>/databases/mac_analyzer_web.db`. Переменная
`MAC_ANALYZER_DATABASE_PATH` заменяет путь к самому файлу и имеет приоритет над
путём каталога данных. Сначала штатно остановите Web-сервер и дождитесь его
закрытия, затем выберите этот `.db` через импорт SQLite в Next. Импорт локально
проверяет SQLite и добавляет поддерживаемые таблицы в IndexedDB текущего
браузера; существующие данные не удаляются, а пропущенные таблицы показываются
в отчёте импорта. Резервную копию исходного файла храните вне папок проекта,
`dist/` и Git; после импорта для дальнейшего переноса выгрузите архив Next
`.madb.json` в выбранную папку резервных копий или на USB-диск.

В Next импортируйте каждый нужный `.db` отдельно: инженерный режим → «База,
справочники и экспорт» → «Импортировать SQLite». Выбирайте исходный файл через
диалог; не переименовывайте его, не копируйте файлы внутреннего хранилища
браузера и не помещайте SQLite в `dist/`. Импорт проверяет SQLite и добавляет
поддерживаемые записи в IndexedDB.

## IndexedDB текущего браузера

Основная рабочая база хранится в IndexedDB конкретного профиля браузера на этом
компьютере. Это автоматический режим после первого запуска. Другой компьютер,
другой браузерный профиль или приватное окно получают отдельную пустую базу.
Один и тот же HTML не может сам найти базу в профиле другого компьютера.

Метаданные каждого успешного Final включают время наблюдения, список исходных
файлов и длительность обогащения (`processingTimeMs`). Схема 14 сохраняет
исходный Blob каждого Main/SmartRoom/DDIO до 64 МиБ в `originalFiles`, связанном
с Final по стабильному ID и роли; запись идёт в той же транзакции, что и новый
Final. В каталоге Final доступны кнопки скачивания сохранённых оригиналов.
Ключ повторного импорта включает потоковый SHA-256 каждого файла, поэтому
совпадение имени, размера и `lastModified` при другом содержимом не переиспользует
чужой Final.
`listOriginalFiles` выдаёт только метаданные, `getOriginalFile` читает один
оригинал. Миграция v13→v14 добавляет store без изменения существующих снимков.
Миграция v14→v15 добавляет `singleAnalyses` и `singleAnalysisChunks`, не меняя
Final, Inventory или History.
Portable JSON archive и синхронизация выбранной папки включают содержимое
`originalFiles`: исходные байты входят в optional root collection `originalFiles`
с Base64 блоками по 192 КиБ, поэтому старые v1 архивы остаются совместимыми,
а новые экспортируют оригиналы потоково.
Файлы очереди локальных расписаний, которые лежат в `fileHandles`, также
переносятся в optional root collection `legacyTaskQueueFiles` блоками по
192 КиБ. Импорт собирает Blob в локальном хранилище и связывает его с той же
записью очереди; байты и имена не попадают в журналированные preview. Размер
проверяется потоково, а превышение квоты IndexedDB отменяет импорт без замены
активного Final. Архивы v1 без этой коллекции продолжают импортироваться.
Совместимый `Database.importArchive()` object API также проверяет связь файла
с записью расписания и размеры блоков, затем сохраняет Blob и очередь в одной
IndexedDB-транзакции.
В инженерном режиме кнопка «Восстановить исходники в объединение» для снимка
подготавливает его Main/SmartRoom/DDIO файлы в экране «Объединение данных».
Все файлы сначала проверяются и читаются; только после успешной подготовки они
заменяют текущий выбор, причём приложение просит подтверждение, если там уже
есть выбранные исходники. Это локальная операция и не запускает объединение.

Для перенесённого рабочего пространства MAC Analyzer Pro раздел «Объединение
данных» показывает сохранённые сводки исходников. Архив не содержит локальные
пути и байты этих файлов: выберите нужную сводку и вручную укажите исходный
CSV/TSV/TXT/JSON/XLS/XLSX/XLSM-файл с компьютера. Для Excel-книг используется лист,
записанный в сводке. Приложение читает его локально, восстанавливает распознанные
роль и допустимые сопоставления колонок; перед
объединением проверьте их в обычной форме. Если исходного файла больше нет,
его содержимое нельзя восстановить из одной сводки.

Отчёт анализа одного файла хранится отдельно в `singleAnalyses` и
`singleAnalysisChunks`. Метаданные содержат сводку, mapping, имя файла, время,
счётчики и ID связанного снимка `Single file`; распознанные устройства и
диагностика записываются порциями по 500 строк в одной строгой IndexedDB-
транзакции. Снимок, исходный файл, Inventory и события сравнения записываются
отдельной транзакцией `saveFinal` без смены активного Final. Сравнение проверяет
кандидатов накопительного Inventory, а непопавшие в частичный файл устройства
не считаются отсутствующими. История отчётов ищется и показывается страницами,
переносимый архив экспортирует и добавочно восстанавливает эти записи.
Повторяющийся ID при восстановлении сохраняет уже имеющийся анализ.

Временная статистика
читает SnapshotChunks порциями и не меняет активный Final или содержимое базы.
При запуске активная ссылка проверяется по метаданным и каждому ожидаемому
чанку. Если ссылка потеряна или её Final повреждён, приложение выбирает самый
новый полный снимок и обновляет только указатель. Неполный Final не загружается
как успешный, а повреждённые данные не удаляются. Если целого снимка нет,
приложение оставляет указатель доступным для повторной проверки при следующем
запуске и сообщает, что активный Final недоступен.

В версии схемы 8 есть отдельное хранилище `smartroomRoomMappings`: для каждого
нормализованного Smartroom ID оно сохраняет последнее однозначное помещение
или конфликт, имя/ID исходного Final, дату и до пяти MAC-примеров. Запись
попадает туда в транзакции успешного Final и переносится в `.madb.json`.
Однозначные связи заполняют только пустое поле `room`; текущие значения из
файлов и `Previous Final` остаются приоритетными. Исторические dashboard и
временные агрегаты лежат в отдельном IndexedDB `analyticsCache`; при изменении
состава Final этот кэш очищается в той же транзакции. В схеме 8 локальные
именованные архивы используют каталог `archives` и постраничное хранилище
`archiveRecords`. Создание проверяет целостность Final и обнаруживает изменения
базы во время копирования; частичный черновик очищается при ошибке.

Схема 9 добавляет отдельный `fileHandles` для локального File System Access
handle. Эти browser-specific записи не входят в portable archive; миграция с v8
сохраняет существующие Final, Inventory и настройки.

Схема 10 добавляет индекс History `by_device_timestamp` для постраничного чтения
событий одного устройства. Миграция v9→v10 проходит записи курсором и
нормализует `timestamp` из даты события или снимка, когда поле отсутствует;
существующие события и другие хранилища сохраняются. Карточка устройства
загружает историю по 100 событий, показывает точное число записей и дозагружает
следующие страницы. HTML-экспорт последовательно проходит все страницы.

Схема 11 добавляет в Inventory `observationCount`. При миграции v10→v11 сначала
обнуляется счётчик записей, затем SnapshotChunks читаются курсором по одному
чанку и увеличивают счётчик соответствующего устройства. Новые успешные Final
увеличивают его в той же атомарной транзакции, что сохраняет snapshot и Inventory;
повторно распознанный source key снимок не дублирует и счётчик не меняет. Поле
переносится в portable archive и отображается в отчёте одного устройства.

Схема 12 добавляет индексы Inventory `by_switch` и `by_alternate_mac`.
Индекс альтернативных MAC использует `multiEntry`; миграция v11→v12 строит их
по существующим записям без удаления Inventory. Если внутренний ID отсутствует,
поиск исторического кандидата проверяет основной и альтернативные MAC, а
двусмысленный результат остаётся диагностикой.

Схема 23 добавляет индексы Inventory `by_device_id` и `by_serial_identity`.
Миграция v22→v23 сохраняет существующие строки. Поиск исторического кандидата
проверяет ID, Device ID, серийный номер, основной и альтернативные MAC с
ограниченным числом совпадений на каждый ключ. Отдельный анализ сравнивается с
накопительным Inventory и не помечает устройства вне частичного файла
отсутствующими.

Схема 24 добавляет индекс `by_query_metric_count` к временному хранилищу
`legacyObservationQueryScratch`. Миграция v23→v24 сохраняет уже записанные
наблюдения и добавляет только индекс. Выбранный Final использует то же хранилище
для точных счётчиков групп кластеризации и ранжирующих метрик производителя,
модели, помещения, Smartroom ID и коммутатора. Данные сливаются из чанков,
top-50 выбирается полным курсорным проходом с ограниченным буфером, а кластеры
читаются страницами и CSV записывается последовательными порциями. Удаление
Final очищает только его производные агрегаты; очистка снимков очищает всё это
производное хранилище.

Схема 25 добавляет `by_query_metric_rank` по `(queryId, metric, rankCount,
value)`. Миграция v24→v25 сохраняет все scratch-строки и только добавляет индекс.
Миграция v25→v26 добавляет курсорные `deviceIdKey`/`serialKey` значения и
индексы для поиска Inventory по нормализованным сильным идентификаторам. Старые
Device ID/serial индексы сохраняются для совместимости, а Inventory строки и
прочие хранилища не удаляются.
Миграция v26→v27 добавляет `by_device_type` для точного счёта событий типа
`modified` по устройству; существующие History-записи остаются без изменений.
Для сохранённого Final в scratch лежат точные счётчики коммутаторов, портов и
помещений по каждому коммутатору. Ранжированный cursor даёт страницы switch
summary, а primary-key cursor — страницы портов и помещений; состав устройств
по-прежнему читается из Final страницами по 50.

Отчёт об изменениях IP коммутатора сравнивает кандидатов Inventory партиями по
250 и записывает найденные строки в `legacyObservationQueryScratch` теми же
ограниченными партиями. Интерфейс читает по 100 строк курсором и считает полный
итог через `count`, не удерживая полный список изменений в памяти. Эти строки
временные, не входят в переносимый архив, удаляются при следующем отчёте; записи
после аварийно закрытой вкладки очищаются при старте после истечения суток.

В разделе «База, справочники и экспорт» кнопка «Экспортировать весь Inventory
в XLSX» читает IndexedDB страницами по 500 записей. Экспорт включает ID,
MAC, последние известные поля, даты, присутствие и `observationCount`; большие
каталоги разделяются по листам Excel. Книга записывается потоком в ZIP/OOXML:
строки не собираются в один массив, XML использует inline strings, а CRC и ZIP
каталог создаются на лету. Если число записей изменилось за время экспорта,
файл не предлагается как полный и приложение просит повторить операцию.

Раздел «Локальные архивы состояния» сохраняет архив в текущем профиле браузера.
Его можно потоково выгрузить как обычный переносимый `.madb.json`, восстановить
с добавлением отсутствующих записей или удалить. Восстановление не удаляет
снимки и не заменяет более новые локальные записи; оно добавляет историю при
совпадении авто-ID, сохраняет приоритет новых Inventory и выбирает активный
Final по дате наблюдения после завершения слияния.

## Переносимый архив

В разделе «База и экспорт» используйте «Выгрузить архив», перенесите созданный
`.madb.json`, затем выберите его кнопкой «Загрузить архив» на другом компьютере.
Импорт сливает снимки и справочники по стабильным ID и не удаляет существующую
базу. Более старый архив не заменяет более новый активный Final, локальные
известные поля Inventory или существующие настройки. История с совпавшими
авто-ID добавляется отдельными событиями. Перед записью проверяются версия,
структура, повторяющиеся ID и общий предел записей.

Экспорт читает Final порциями по 500 устройств, а Inventory, History и справочники
проходит IndexedDB-курсорами по страницам. JSON поступает в Blob потоком, без
промежуточных массивов полной базы. Импорт вручную и восстановление из выбранной
папки сначала сканируют JSON слайсами и проверяют формат/версию, затем потоково
разбирают коллекции и Final-чанки, записывая их во временный staging в IndexedDB.
После успешной проверки staging добавочно сливается по стабильным ключам и
удаляется диапазонным IndexedDB delete. Ограничения — 4 ГиБ и два миллиона
записей; несегментированный вспомогательный JSON reader ограничен 256 МиБ.

## Выбранная папка данных

В поддерживаемом Chrome/Edge можно кнопкой выбрать папку в защищённом
контексте. Браузерное разрешение запрашивается во время этого действия; handle
папки хранится отдельно в IndexedDB и не попадает в portable archive. На каждом
старте приложение проверяет сохранённое разрешение. Если браузер его сбросил,
в шапке появляется кнопка повторной авторизации без повторного выбора папки.

В папке используется `mac-analyzer-data.madb` с обычным portable archive внутри.
При запуске архив проходит ту же проверку и additive import, что и ручной импорт:
более новые Final и пользовательские записи остаются сохранены; invalid archive
не заменяется обратной выгрузкой. После успешного импорта и изменений Final,
mapping или справочников portable archive записывается потоком. В браузерах
без File System Access остаётся явный путь выгрузки и импорта portable archive.
Исходные Blob из `originalFiles` входят в потоковый папочный и portable archive.
Browser smoke folder mode ещё требуется.

Пока вкладка приложения открыта, активный Final автоматически экспортируется
потоковым XLSX в ту же папку каждые пять минут. Для каждого файла используется
отдельное имя с датой, временем и случайным суффиксом; приложение проверяет
разрешение папки перед каждой записью и не запрашивает его из фонового таймера.
Если браузер отозвал доступ, сохранение пропускается до повторного разрешения
через кнопку в шапке. Эти XLSX являются дополнительными экспортами Final; они
не заменяют IndexedDB и не содержат весь workspace.

## Общая база по сети

Опциональный HTTP-host запускается через `START_MAC_ANALYZER_SERVER.cmd` и
публикует только standalone HTML с loopback-адреса `127.0.0.1`; `/api/health`
используется launcher-ом до открытия браузера. Выбранный порт сохраняется в
`%LOCALAPPDATA%\MAC Analyzer Pro Next\local-server-port.txt`, чтобы origin и его
IndexedDB оставались теми же при следующих запусках. Если сохранённый порт занят
чужим процессом, launcher останавливается с ошибкой, а не переключает приложение
на другой origin. `STOP_MAC_ANALYZER_SERVER.cmd` останавливает host через
loopback-запрос с одноразовым случайным токеном; запрос без токена не завершает
процесс. Токен хранится в `%LOCALAPPDATA%\MAC Analyzer Pro Next\local-server-stop-token.txt`
и удаляется после успешной остановки. Этот optional host не предоставляет SQLite
API и не принимает данные устройств. Основной запуск через HTML остаётся автономным, а сохранение
по-прежнему принадлежит IndexedDB конкретного browser profile и origin; HTTP-host
не делает базу общей между компьютерами. Общая SQLite-база потребует отдельного
backend API, backup, конкурентной записи и документации безопасности. До этого
обмен между профилями выполняется переносимым архивом.

## Импорт файлов

Автономный importer принимает до 64 MiB на входной файл, до 150 000 строк и
1 500 000 ячеек, а XLSX/XLSM — до 10 000 ZIP-частей, 128 MiB на часть и
192 MiB суммарного распакованного содержимого. CSV/TSV/TXT/JSON и XLS/XLSX/XLSM
останавливаются с ошибкой, если лимиты превышены. XLSX ZIP-каталог читается
срезами, сжатые части распаковываются потоком, а worksheet-строки и shared
strings обрабатываются по одному XML-элементу. Для Main, SmartRoom и DDIO
интерфейс держит только preview до 100 строк; при обогащении поддерживаемые
CSV/TSV/TXT/JSON/XLS/XLSX/XLSM читаются заново пакетами по 500 строк. Так что
полный массив исходных строк импортируемой таблицы не остаётся в памяти. При этом
нормализованные устройства Main, индекс DDIO, Previous Final, текущий Final и
данные сравнения пока материализуются для глобального сопоставления. Enrichment
повторно использует принадлежащие ему нормализованные записи как Final вместо
создания второй полной копии массива устройств и объектов; потоковая передача
устройств по всему pipeline остаётся открытой задачей. Справочники OUI, известных моделей, MAC5 и
vendor/model history загружаются и применяются последовательно порциями до 500
MAC, чтобы не создавать полные списки MAC и lookup-Map для всех устройств сразу.
Регрессия проверяет границу пакета и точное покрытие 1001 устройства для каждого
справочника.
Индекс DDIO также фильтруется сильными MAC/Device ID текущего набора устройств
во время чтения строк; посторонние записи не занимают место в индексе, а счётчик
прочитанных DDIO-строк остаётся полным.

JSON-экспорт анализа одного файла и сравнения файлов сериализует вложенные
массивы по элементам и отправляет текст кусками до 256 КиБ. В поддерживаемом
браузере данные записываются сразу в выбранный файл с backpressure; fallback
собирает Blob из тех же ограниченных строковых порций без единой полной строки.

Вложения очереди, перенесённые из legacy SQLite, могут оставаться в отдельном
локальном IndexedDB-хранилище SQLite. При portable `.madb` экспорте приложение
находит это хранилище по namespace расписания, читает Base64 небольшими блоками
и добавляет файл в архив как локальное вложение. Если исходная SQLite-база уже
недоступна, экспорт явно сообщает об ошибке, чтобы не выдать неполный архив.
