# Архитектура и принцип работы

## Поток данных

```text
Main + SmartRoom + DDIO
          │
          ▼
  Import и выбор колонок
          │
          ▼
  Нормализация значений
          │
          ▼
 Единая идентификация устройства
          │
          ▼
 Стратегия NO_EXPANSION / ALLOW_EXPANSION
          │
          ▼
 Previous Final + OUI + Known Models + DDIO IP
          │
          ▼
 Working Final → Validation → IndexedDB transaction
          │
          ├── Final Snapshot
          ├── Inventory
          ├── History
          └── Analytics cache
```

## Принципы

1. **Основной файл задаёт состав.** В `NO_EXPANSION` дополнительные источники
   не создают устройства. В `ALLOW_EXPANSION` новые устройства может создавать
   только достоверная SmartRoom-запись. DDIO всегда является источником атрибутов.
2. **Final и Inventory разделены.** Final описывает текущий цикл, Inventory — все
   когда-либо известные устройства.
3. **Одна точка создания устройств.** Любой кандидат проходит через
   `resolveOrCreateDevice`; парсеры никогда не добавляют Final-строки напрямую.
4. **Пустое не стирает известное.** Previous Final используется для заполнения
   пропусков, но отсутствующие сейчас устройства не возвращаются в активный Final.
5. **Сильные идентификаторы важнее слабых.** Сохранённый внутренний ID,
   Device ID, serial и MAC имеют приоритет. Hostname, IP и помещение без сильного
   подтверждения не объединяют записи.
6. **One-to-many остаётся коллекцией.** Possible IP, порты, альтернативные MAC и
   конфликты не превращаются в отдельные устройства.
7. **Атомарность.** Новый снимок становится активным только после успешной
   транзакции IndexedDB. При ошибке последний успешный Final не меняется.
8. **Предсказуемая аналитика.** Все KPI и графики строятся из полных Final-снимков,
   а не из текущей страницы таблицы.

## Модули

- `src/core/normalize.js` — нормализация MAC, IP, текста, дат и пустых значений.
- `src/core/identity.js` — единые ключи, оценка совпадений и стабильные ID.
- `src/core/enrichment.js` — централизованный pipeline обогащения.
- `src/core/comparison.js` — Final-to-Final сравнение и история изменений.
- `src/core/analytics.js` — KPI, графики, помещения и отклонения коммутаторов.
- `src/data/importer.js` — CSV/TSV/TXT/JSON/XLS/XLSX, даты файлов и автоопределение колонок; legacy XLS декодируется локальным SheetJS BIFF parser с ограничением 16 MiB.
- `src/data/database.js` — версионированное порционное IndexedDB-хранилище.
- `src/ui/render.js` — безопасный DOM-рендеринг, таблицы, модальные окна и canvas.
- `src/app.js` — только координация пользовательских сценариев.

## Производительность

- таблица показывает одну страницу вместо тысяч DOM-строк;
- поиск использует предварительно построенную строку-индекс;
- snapshot хранится блоками по 500 устройств;
- история snapshot изменений и MAC-churn агрегируется в автономном Web Worker;
  чанки IndexedDB передаются последовательно с подтверждением каждого блока,
  устаревшие запросы прекращают чтение, а при недоступном Worker используется
  тот же агрегатор в основном потоке;
- тяжёлые циклы регулярно уступают главный поток через `scheduler.yield` или
  `setTimeout(0)`;
- аналитика кешируется по паре ID снимков и инвалидируется при сохранении Final;
- DDIO, identity и OUI используют `Map`, а не вложенные полные сканирования.
- пара Final для dashboard публикуется только после успешной загрузки обоих полных снимков;
  если за это время выбран другой Final или обновилась база, старый запрос отбрасывается.
